Project Tracking

IDS Area owner: Hanna Kultima, Lars Feuk · Project leaders: Moa Borén, Wojtek Potrzebowski
Status: Feasibility study completed; preparing for project launch / implementation phase.
Resources: Project leads; data/system architect; backend/API developer; data steward / metadata specialist; unit champions; Architecture Board input; UX/service design input.

Scope

A shared project-data foundation that aligns project information from heterogeneous SciLifeLab unit systems and makes it usable for users, staff and management. The immediate priority is that foundation and a staff-facing use case. A broader user-facing service remains a later step.

Out of scope

A user-facing interface as the first-phase product; full User Portal functionality; replacement of ordering, billing or LIMS systems; duplicating IAM, identifier services, FAIR metadata, data transfer or repositories; complex workflow automation beyond basic statuses and milestones.

Value

  • Give users a clear project overview (status, next steps, contacts) to reduce email back-and-forth. Support time management, planning, and adapting to changes.
  • Provide staff and unit leadership with a shared view of project portfolios, workloads, and bottlenecks for planning and reporting. Reduce reporting effort and enable on-demand report creation.
  • Provide SciLifeLab with comparable cross-platform project data and evidence to inform future User Portal and IDS developments.

Data governance

Governance is a prerequisite and must be clear enough to guide architecture. Across participating organisations this covers ownership and responsibility, access, retention, permissions and management.

Identifiers

The foundation needs stable UserID, ProjectID and UnitID, and a way to connect unit-specific work packages and sessions to the common project. These come from shared identifier services rather than a parallel scheme.

Main deliverables

  • Minimum common project data model.
  • Project database and data layer.
  • APIs and adapters to unit systems.
  • Data collection and integration playbook.
  • Staff-facing dashboard as a subsequent layer and pilot. It consumes the common data and API; it does not define them.

Pilot success

Validate the common model with real unit data and workflows, connect selected pilot systems, demonstrate useful cross-unit information, and pilot the staff dashboard.

Dependencies

Integrate with these IDS efforts rather than duplicating them:

  • Identity and Access Management / LifeScience ID and role models (including privacy, security and audit).
  • Project and sample identifier services (e.g. BioSamples/EMBL-EBI instance, RAiD).
  • FAIR Data & Metadata.
  • Data transfer and delivery.
  • Repositories.
  • Broader IDS architecture and digital services.
  • Order Portal and relevant unit systems, as sources to connect.

High-level architecture

Simplified view of the project tracking service, integrating existing unit systems (Order Portal, iLAB, FMS, others) into a central project database and web interface.
